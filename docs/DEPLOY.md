# VocabVault Deployment (all-free: Render + Cloudflare Pages + Atlas M0)

> Total cost: $0/mo. Secrets rule: values live only in dashboards and your
> local shell — never in git, screenshots, or chat. Rotate a secret the moment
> it leaks anywhere public.

## 1. Atlas — production database + user (~2 min, human clicks)

1. MongoDB Atlas → **Database Access** → Add user `vv-prod`, password auth,
   strong generated password. Restrict privileges: `readWrite` on database
   `flashcards-prod` only (not the dev database).
2. **Network Access** → Add IP `0.0.0.0/0` with comment `render-dynamic`
   (Render outbound IPs change; there is no fixed allowlist on free tier).
3. Copy the connection string; replace `<username>`, `<password>`, and the
   database path with `flashcards-prod`. It stays on your machine for step 4.

## 2. Render — API (~5 min, human clicks)

1. [dashboard.render.com](https://dashboard.render.com) → **New → Blueprint** →
   connect the `vocab-vault` repo. `render.yaml` pre-fills everything,
   including `NODE_VERSION=22` and `NODE_ENV=production` — do not remove
   `NODE_ENV`: without it the API boots in dev mode (open CORS, no
   `JWT_SECRET` boot check) and fail-closed protections never engage.
2. Fill prompted env vars:
   - `MONGODB_URI` — the prod string from step 1.
    - `CLIENT_URL` — the canonical web URL `https://vvault.pages.dev`
      (no trailing slash). Comma-separated for multiple origins; every entry
      must start with `http://` or `https://` (others are silently dropped).
      In production a missing `CLIENT_URL` crashes the boot rather than
      serving open CORS. Render redeploys automatically on env change.
   - `JWT_SECRET` — auto-generated by the Blueprint; leave it.
3. Deploy. The deploy succeeds only if `GET /api/health` returns 200.
4. Note the service URL (`https://vocab-vault-api.onrender.com` if you keep
   the default name).

## 3. Cloudflare Pages — web client (canonical: `https://vvault.pages.dev`)

### Primary: Git-connected deploy (auto-deploys on push to `main`)

1. Cloudflare dashboard → **Workers & Pages** → `vvault` → **Settings** →
   **Builds & deployments** → **Connect to Git** → authorize the GitHub App
   → select repo `zaheen4/vocab-vault`, production branch `main`.
2. Build settings (Settings → Build & deployment → Build settings → Edit):
   | Field | Value |
   |---|---|
   | Production branch | `main` |
   | Build command | `npm run build -w client` |
   | Output directory | `client/dist` |
   | Root directory | `/` (leave empty — must be repo root, not `client/`, so the workspace lockfile is used) |
3. Environment variables (Settings → Environment variables → Production):
   - `VITE_API_URL` → `https://vocab-vault-api.onrender.com/api` (your real
     API URL from step 2 — Vite bakes this in at build time).
   - `NODE_VERSION` → `22` (required: Pages defaults to Node 18, but Vite 8
     needs Node ≥ 20.19; without this the first Git deploy will fail).
4. Push to `main` (or retry the first deploy) — the build ships `client/dist`
   including `_redirects` (SPA fallback) and `_headers` (security headers),
   plus the 1,110 pronunciation clips in `public/`.

### Fallback: manual upload (one-off, no auto-deploy)

```bash
npx wrangler pages deploy client/dist --project-name=vvault
```

This bypasses Git — useful only if the GitHub App connection is temporarily
broken.  Subsequent pushes to `main` will **not** trigger a rebuild.

## 4. Seed production data (human runs, agent verifies)

On your machine (dataset file is committed, seed is idempotent, custom
content is spared):

```bash
MONGODB_URI='<prod-uri-from-step-1>' npm run seed -w server
```

> The URI's database path must be `flashcards-prod` (dev uses
> `flashcards`) — seeding the wrong database is silent and looks fine.

Verify: `words` → 1,110 documents, `decks` → 37 group decks, and
`https://vvault.pages.dev/audio/words/compound.mp3` returns 200.

## 5. Smoke test (together)

Temp account on the **production** URLs: register → practice one card →
review records (`xpEarned`, streak) → badge/goal fields present → delete the
temp account and its data. Then CORS proof:

```bash
# prod origin: must include access-control-allow-origin
curl -sI -H 'Origin: https://vvault.pages.dev' https://<your-api>.onrender.com/api/health | rg -i access-control-allow-origin
# foreign origin: header must be absent
curl -sI -H 'Origin: https://evil.test' https://<your-api>.onrender.com/api/health | rg -i access-control-allow-origin; echo "(empty = blocked)"
# deploy gate: must report the merged short SHA, not an older one
curl -fsSL https://<your-api>.onrender.com/api/health | python3 -c 'import json,sys; print(json.load(sys.stdin)["deploy"])'
```

> Render posts no commit statuses to GitHub, so a failed prod deploy is
> silent here. The `deploy-gate` workflow covers it: after every `main`
> push touching `server/` or `render.yaml` it polls `/api/health` for up to
> 15 min (20 min job cap) until `deploy` equals the pushed SHA, `status` is
> `ok`, **and** `db` is `true` — then it asserts that
> `Access-Control-Allow-Origin` echoes `https://vvault.pages.dev`. A red run
> prints the last body and where to look. Client-only pushes skip, because
> `rootDir: server` means Render doesn't rebuild for them. Manual re-check
> anytime via Actions → deploy-gate → Run workflow.

## 6. Warming the API: keep-warm cron + demo fallbacks

> Render spins a free web service down after **15 min** without inbound
> traffic and needs ~1 min to come back. Nothing inside this repo can prevent
> that (a merge-time check can't see idle time), so the keep-warm ping is an
> external cron — §6.1 is the setup. §6.2 and §6.3 are the fallbacks for when a
> demo starts on a cold or dead instance anyway.

### 6.1 Keep-warm cron (set once, enable for demo week)

Any HTTP scheduler works. [cron-job.org](https://cron-job.org) free is enough;
UptimeRobot free works too and adds alerting.

1. **URL:** `https://vocab-vault-api.onrender.com/api/health` — `GET`, no
   headers, **no token** (the endpoint is public and must stay that way; never
   paste a JWT into a third-party dashboard). Ping the API, not
   `vvault.pages.dev` — Pages is static and always up, so it wakes nothing.
2. **Interval:** every 5–10 min. It must be **under 15** min; 5 leaves the most
   slack for a late tick.
3. **Timeout:** as high as the plan allows (~30 s). The first ping after a
   spin-down *is* the wake-up and may exceed it — that is a wake, not an
   outage. The next tick confirms.
4. **Alerting:** email after 2 consecutive failures, so a single cold-start
   timeout doesn't page you.
5. **Window:** enable it the day before the demo, disable it afterwards (see the
   budget note below).

Why `/api/health` and not `/api/decks`: it is mounted **before** `apiLimiter`,
so keep-warm pings never eat the rate limit or touch Mongo, and its response
(`status`, `db`, `deploy`) doubles as a health and deploy check.

> **Budget trap.** A workspace gets **750 free instance hours per month**, and
> exhausting them suspends *every* free web service until the next month —
> including on demo day. Keeping one service awake 24/7 for a 31-day month is
> 744 h, and a deploy briefly runs two instances. So:
> - demo week only → 7 × 24 = 168 h, comfortable;
> - all month → restrict the cron window to waking hours (e.g. 07:00–23:00
>   ≈ 496 h) rather than 24/7.
>
> Check `dashboard.render.com/billing#included-usage` before a long stretch of
> warming; Render emails you as you approach the cap.

Do **not** use a GitHub Actions `schedule` for this: scheduled workflows are
best-effort and can be delayed well past 15 min under load — exactly the
failure mode being prevented.

Verify it works: `curl -w '\n%{time_total}s\n' https://<your-api>.onrender.com/api/health`
must return `< 2 s` with `db: true`, and the cron service's history must show
`200` with `status: "ok"`.

### 6.2 If the demo starts and the API is cold

1. ~60 s before showtime: `curl -w '\n%{time_total}s\n' https://<your-api>.onrender.com/api/health`
   - `< 2 s` → warm, go.
   - `30–60 s` → it just woke; immediately hit `/api/decks` once more and go.
2. Keep the app tab open (traffic = awake).
3. Fallback: run `npm run dev` locally and demo from `localhost:5173`
   (pre-rendered audio + Atlas dev data are identical).

### 6.3 If the API is down instead of cold (edge 522, empty reply, curl timeout)

A cold instance answers eventually; a dead one answers nothing. Triage with
`curl -v` before touching DNS or certificates:

1. TLS handshake completes and then **0 bytes** come back on every method and
   path → the instance is dead, not slow. A nonexistent `*.onrender.com` host
   returns a fast 404 instead, so a 522 here is not a typo in the URL.
2. Render dashboard → the service → **Deploys**: no log line for the current
   request and a stale `deploy` SHA in any cached response confirm it. Render's
   status page can be green while your single free instance is wedged.
3. **Manual Deploy → Deploy latest commit** (saving any env var also triggers a
   redeploy). Watch the log for `Mongo connected`, `listening on :10000`, and a
   `Live` timestamp.
4. Re-check: `curl -fsSL https://<your-api>.onrender.com/api/health` must return
   `db: true` and the current `deploy` SHA, then re-run the §5 smoke test.
   Rate-limit headers on `/api/*` confirm `NODE_ENV=production` is set.

> `deploy-gate` verifies **deploys**, not uptime: it runs at merge time and a
> dormant or wedged instance between merges is invisible to it. That's what the
> external cron warm-up and this runbook are for — don't expect a red check for
> an outage nobody pushed.
